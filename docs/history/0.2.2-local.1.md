# DESIGN §31 — Local eight-player parties and text chat

Part of [DESIGN.md](../DESIGN.md) (local extension, not an upstream or official-mode release).

## 31. Local extension: 0.2.2-local.1

Requested by this installation's owner on 2026-10-09: support cooperative rooms with capacities 4–8 and typed chat. This deliberately extends the official four-player mode. The base source and unchanged game assets are from 0.2.2; this version is a local build, not a claim about upstream releases. Generated game data and deterministic battle-engine mechanics are unchanged.

### 31.1 Room and match size

- `MAX_SEATS = 8`. New clients offer room capacities 4 / 5 / 6 / 7 / 8, default 8. `room.create {mode, difficulty, capacity?}` without capacity remains compatible with old clients: co-op defaults to 4, solo to 1. An explicit solo capacity must be 1; an explicit cooperative capacity must be an integer 4–8. `room.state.capacity` is authoritative; the seats array has that length.
- AI teammates take real player seats. Spectators remain separate, capped at two, and are not extra players. Existing readiness/start rules permit a partially occupied room; four humans are not required to start.
- Shared pool copies are frozen using the actual occupied seat count at match creation: `ceil(originalCopies * max(1, players / 4))`, capped at eight players. Leaving, disconnecting, or elimination does not shrink the pool; solo and 1–4 player pools are unchanged.
- Each player keeps a separate board. Boss fields still pair players, with an odd player alone, and all fields share the Boss HP pool. Per-field battle-result limits are not raised as if eight players shared one field.

### 31.2 Draft and difficulty scaling

- Cooperative special drafts with more than four alive players offer `players + 2` independently indexed slots, at most ten. Extra slots duplicate only legal cards already generated for that round/family. Remaining picks/default picks, index validation, UI normalization and audit bounds use the expanded slots. The 1–4 player and solo RNG paths remain unchanged.
- The existing `bossHp.perPlayer` branch scales with the actual alive count up to eight; the legacy fixed-pool / alive-scaling compatibility branch retains its four-player reference.
- Hidden-core eligibility uses the alive-player count frozen when Boss preparation ends, not the count after the Boss dies. The cooperative base threshold scales by `max(4, aliveCount) / 4`; solo is unchanged. This is a local balance decision, not an official eight-player rule.
- Cooperative 联防 progress `left` is a map of source leakers from the whole party (up to eight structural keys), unlike per-field `perPlayer` reports. Both browser and scripted-client serializers must retain more than four source players.

### 31.3 Room-scoped text chat

The existing WebSocket carries chat; there is no extra chat server/database. The lobby owns routing, identity, membership and moderation, so seated humans can send during waiting, briefing, strategy draft, combat and settlement, including eliminated players until they leave. Spectators may read but not send. A removed or departed member cannot send.

C→S:
- `chat.send {clientId, text}` → `ok` or `error`. The server derives room, player ID, nickname, seat and timestamp; it never trusts these fields from the sender.
- `room.chatMute {playerId, on}` → host-only mute/unmute of a human in the same room, including during a match. `on` is explicitly boolean. Muted sending returns `CHAT_MUTED`.

S→C:
- `chat.message {code, id, playerId, name, seat, role:'player', text, at}` → same room's seated members and spectators only; monotonically increasing room-local IDs.
- `chat.history {code, messages, lastId}` → latest 100 messages on create/join/spectate/resync, not every ordinary room-state broadcast.
- `room.state.mutedPlayerIds` → authoritative current moderation state.

Messages are trimmed and control characters removed. Empty text is rejected; maximum 200 Unicode code points and 1024 UTF-8 bytes, without silent truncation. A session may send at most one new message per second across reconnects; a room allows at most ten new messages per rolling second. Same session/room/clientId retries acknowledge without rebroadcast or consuming another rate slot. The bounded dedupe window retains at most 100 IDs per session/room; history is bounded to 100. Room destruction clears chat state. Messages/history are memory-only and do not survive a server restart.

### 31.4 Client behavior

One app-level chat panel survives room/match phase transitions. It folds away, shows unread counts, merges history/live messages by ID, clears on room changes, and displays nickname plus P1–P8. Text and names render as text nodes, never HTML or auto-linked content. Disconnection, spectator status and mute disable sending; failed sends retain the draft and show a translated error. Host controls use explicit mute/unmute actions.

Enter sends, Shift+Enter inserts a newline (controls are normalized on send), Escape folds the panel. Composition state, `isComposing` and key code 229 prevent an IME candidate-confirming Enter from sending. Gameplay hotkeys do not act while typing or focusing chat controls; modal Tab/Escape accessibility is preserved. Eight seats, team rows, statistics and ten draft cards remain reachable with responsive layouts.

### 31.5 Verification and rollback

Targeted tests cover capacities, session/membership isolation, moderation, bounded history/dedupe/rate limits, Unicode/IME/plain-text UI behavior, draft legality/indexes/audits, 4–8 player match state machines and eight scripted clients running the real simulation. A separate real WebSocket/browser smoke must exercise actual eight-seat networking and chat, and is not a claim of eight physical devices playing a sustained match.

Keep the old image and source/config/assets backup before switching. A restart ends in-memory rooms and matches; switch only when the production health endpoint reports no active match. Low-power deployments keep `SP_COMBAT=client` and `SP_VERIFY=off`; many AI/disconnected-player takeovers are more expensive than connected browser clients. Chat and gameplay state are not durable storage.
